## Short summary

My bilingual (PL/EN) site, for people considering me for a backend or AI role or a project. It shows my work history on a to-scale timeline, my research with interactive figures, and my teaching with quotes from students. Visitors can check from their own browser that each project's server responds, and ask Vex, an assistant that answers from the site's content.

## Problem

Nothing was missing. The site is one more layer for showing Dawid's skills and interests.

The site's own copy names its audience: people looking at a backend or AI role, or a project. It brings together two sides of Dawid, a Python backend engineer and a PhD candidate in harmonic analysis. Its stated aim is that a visitor can check his projects live and see how they work in practice.

## How it works for the user

This describes the redesign, which is not deployed yet. The version on dawidhanrahan.com has only three pages: Home, Experience and Academic.

1. **Home.** The opening is written as a theorem: "Mathematician by training, engineer by trade". Three proof lines lead to Education, Experience and Projects. Next to them is a box for asking Vex a question.
2. **Projects.** Each project runs at its own address and shows a screenshot, its stack, and a code link or a "private code" note. "Check it live" makes the visitor's own browser contact the project's address. The result is "answers · N ms" or "no answer", and the check gives up after 8 seconds. It shows only whether the server replied, not whether the page works. Each project also has an "Ask Vex about {title}" button.
3. **From the workshop.** Short articles of three kinds: figure, from production, proof. Each shows a reading time. A piece written in one language appears in the other with a note, not a machine translation. The only piece in the repository is a draft, and drafts never reach the live site, so the section is empty for now.
4. **About and contact.** The about text links to the three subpages. Contact offers email, GitHub and a chat with Vex.
5. **Experience.** A to-scale timeline of roles at Nokia, PeakData, Xperi and CloudFerro, with achievements and technologies for each. Visitors can ask Vex about each company.
6. **Research.** Interactive figures with sliders and a play control: heat spreading along a segment over time, a "map of influence" on a cone, a chart of a model's accuracy (the visitor first guesses the training step at which it starts handling new examples, then checks), a clock example, and a wave on a circle that can be shifted. The page also lists published papers.
7. **Education.** Degrees, plus students' quotes about Dawid's teaching.
8. **Vex.** A chat on every page. It answers from the site's content, and the reply appears as it is written. It offers starter questions, such as one about the PhD. After 30 seconds of silence it shows an error and suggests email instead.
9. **Language.** A PL/EN switch; the browser remembers the choice.

## Technical description

One repository with two halves, each with its own toolchain, Dockerfile and Railway config.

**Backend** (Python 3.13, Django 5.2, Django REST Framework, PostgreSQL with pgvector, uv):

- Three domain apps: `work` (skills, projects, experience), `university` (schools, publications, testimonials), `vex` (conversations, documents, prompt configuration), plus `utils` for shared helpers.
- All content lives in the database and is edited in the Django admin. django-parler keeps translations in the database. The frontend has no i18n library; it sends the chosen language as an `Accept-Language` header.
- API: `/api/work/`, `/api/university/`, `/api/vex/`, an OpenAPI schema with Redoc docs, `/healthcheck/`.

**How a Vex question travels:**

1. The widget POSTs to `/api/vex/chat/` and gets a session key and a CSRF token.
2. It opens an `EventSource` on `/api/vex/chat/stream/` with the question, session key and language.
3. The backend sends a `received` event, streams the answer in chunks and ends with `finished`. Any exception becomes an `error` event.
4. A LangChain chain, built once per process, combines context, prompt, an OpenAI chat model and conversation history stored in Postgres per session.
5. Context comes from two sources: similarity search in pgvector (6 chunks by default, filtered by language) and direct table reads. The question is split into words and matched against a PL and EN keyword list. On a match, up to 10 rows are read from the relevant table (skills, projects, experience, schools, publications, testimonials).
6. A configuration record edited in the admin holds the prompt wording, per language, and the model and temperature, shared by all languages. Without one, the code uses `gpt-4o-mini` at temperature 0.5.

**Document ingestion.** An admin action splits an uploaded file into 1200-character chunks (150 overlap), tags them with a language, adds them to the pgvector collection (`text-embedding-3-small` embeddings) and marks the document as loaded so it is not added twice.

**Frontend** (React 18, TypeScript, Vite, Tailwind, shadcn/ui, Vitest):

- Routes in the redesign: `/`, `/experience`, `/research` (the old `/academic` redirects there), `/education`, `/workshop`, `/workshop/:slug`. All except home are lazy-loaded.
- Much of the chat widget protects the stream: it repairs Markdown split across chunks on every render and treats 30 seconds of silence as a failure.
- Workshop articles are Markdown files read at build time. Drafts (`*.draft.md`) are read only by the dev server.
- The research figures keep their maths in separate, tested modules. The HeatField motif is a sum of heat kernels drawn on a canvas. It responds to the pointer and stays still under `prefers-reduced-motion`.
- The look follows the "Binary Axis" visual identity kit, v5.1, versioned in the repository: one light palette, Manrope and IBM Plex Mono, a 1160 px column, and writing rules.
- Project documents in `frontend/src/content/projects/` are meant to feed the home page and Vex. No code reads them yet. How they will reach Vex is not decided; possibly through the admin panel.

## Engineering decisions

- **Hybrid retrieval.** Vector search is combined with rows read straight from the tables, so questions about skills or projects get live database content, not only uploaded documents. The approach considered was a vector database alone. Graph-RAG is worth considering in future.
- **Stanza replaced by a regex tokenizer**, for performance. The commit title says it improved RAG performance significantly. No measurements were recorded.
- **Prompt and model kept in the database**, editable in the admin rather than hard-coded. The prompt is per language; the model and temperature are shared.
- **SSE over a GET EventSource**, opened in two steps: a POST for the session key, then the stream.
- **Media moved from a Railway volume to a private S3-compatible bucket (Tigris).** A volume does not survive a move between projects and cannot be shared between services. Files are served through presigned URLs. ACL headers are off because Tigris rejects them. CI sets `USE_S3` explicitly instead of supplying dummy bucket values, so production fails loudly if its bucket config is missing. The change also found that `STATICFILES_STORAGE` had been ignored since Django 5.1, so Whitenoise's compressed static files had not been active in production. The setting moved into `STORAGES`.
- **Frontend history kept through the merge.** Instead of copying the code in one commit, the history was rewritten into a subdirectory (`git filter-repo`) and merged, keeping 71 commits of history. The cost: two root commits, and the branch had to land as a merge, not a squash.
- **CI tests run on pgvector/pgvector:pg17, not postgres:17-alpine.** On the plain image any pgvector test could fail only in CI, so none could be written. A distance-query test was added that fails on the old image and passes on the new one.
- **Frontend CI: one ordered job instead of three chained ones.** Each job spent about 15 s on setup for 2–9 s of work. The backend deliberately keeps pylint and mypy in parallel: 82 s against 97 s merged, and Actions minutes are free on a public repository. The `branches:` filter was removed because it skipped stacked PRs. Added: cancellation of superseded runs, 10-minute timeouts and read-only tokens.
- **Actions pinned to commit SHAs**, kept current by Dependabot.
- **Every command defined once in the Makefile.** CI calls the same targets, so local commands and CI cannot drift apart.
- **Node 24 for builds.** Node 18 is end-of-life, and Node 22's maintenance window closes in April 2027.
- **Markdown repair skips code blocks.** Blocks are swapped for placeholders during the repair. This fixed two defects first recorded as expected-failure tests: a duplicated empty code block, and lists breaking inside code. A test asserts the function is idempotent, since it runs on every render.
- **Lovable leftovers removed**, and the `vex` app linted for the first time. A pylint `ignore-paths` pattern had been read as a regex and excluded nothing.
- **Live checks run in the visitor's browser**, with `no-cors`. The page says plainly what it measures: reachability and timing only, from whose browser. What matters is the visitor's own experience, not the server's.
- **Drafts excluded from builds** at import time, so an unpublished piece cannot leak in the bundle. Publishing means renaming the file.
- **No dark theme**, because the visual kit defines none.
- **HeatField breaks the kit's motion rule on purpose** (the kit allows only an 8 px rise on entrance). The exception is documented.

## Running it in production

- **Hosting.** Backend and frontend run as separate services in one Railway project, built from this repository.
- **Backend.** Built from a Dockerfile. Migrations run before each deploy. Start-up: compile translations, `collectstatic`, then gunicorn with 2 workers and a 120 s timeout. Railway checks `/healthcheck/`.
- **Frontend.** Multi-stage Node 24 build. The API address and mock mode are baked in at build time, so changing them needs a rebuild. `serve` serves the bundle.
- **Files.** Media goes to a private Railway bucket (Tigris), served through presigned URLs. Whitenoise serves static files.
- **CI.** Three GitHub Actions workflows, each run only for the half that changed: backend (lint, type checks, tests on pgvector with an 85% coverage gate), frontend (format, test, lint, build) and hygiene (Lefthook). Coverage goes to Codecov.
- **Lesson from deploys.** The Railway config file path is resolved from the repository root, not the service's directory. A wrong path fails the deploy with "service config not found" before any build starts.
- **Failure mode.** Vex needs credit on the OpenAI account. Without it the stream opens and then returns an error. The rest of the site keeps working.
- **Upkeep.** Beyond Railway's health check there is no technical monitoring; Dawid watches the number of visits. Running costs are a few dollars a month, OpenAI included. Dawid knows of no incidents. The chat model in production is GPT-Luna (OpenAI).

## Limitations and what's next

- Vex does not answer without an OpenAI key that has credit.
- Content lives in the database, not the repository. A fresh install shows an empty site, since there is no seed data.
- Frontend tests cover logic only. There are no component or end-to-end tests.
- No dark theme, and no success or error colours. The visual kit leaves both for later.
- The redesign is unreleased: 25 commits off `main`, many uncommitted changes, and the only workshop piece is a draft.
- Ingesting uploaded files into Vex does not work with S3 storage (found by reading the code, not by running it). The action reads the file from a local path (`file.path`), and the S3 backend raises `NotImplementedError` for that. Production uses S3 by default, so ingesting an uploaded file there fails. Documents given only as a URL are still ingested.
- Next steps: Dawid wants to focus on the Workshop section and use it to make science, mostly mathematics, more popular.
